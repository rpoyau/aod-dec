# Reusable generated GPU session

Owned changes: `native/gpu_compiler.py` and `tests/test_gpu_compiler.py` only. No AOD/DEC source law, native field updater, boundary law or trace semantics was changed.

`GpuBatchSession(program, opt=0)` snapshots validated source. `run(function, rows, fuel=100000, max_depth=128, param_types=None)` executes the same source-derived kernels while retaining an owning CUDA context, source-bound modules for up to 64 eligible entries, and five bounded reusable device buffers. `close()` and context-manager exit release resources. The original `run_gpu_batch` API now creates, runs and closes one such session; its total includes final close.

Every call still validates exact row types, signed integer domain, source/interface bindings and logical fuel/depth. The session caches compiled code and allocation capacity, never model answers. Every actual row is executed and copied back in input order. Reusing larger buffers copies only the current row count and cannot publish stale rows. Returned profile metadata is copied, so caller edits cannot alter cached compiler bindings. Source changes invalidate execution; caller edits to the original input IR cannot mutate the stored source snapshot.

A session serializes run/close using an owning lock. It creates or pushes its context on the calling thread and pops it on exit, restoring any pre-existing caller context. The context stays detached between calls and may migrate to another thread. This follows NVIDIA's documented context stack and migration semantics: https://docs.nvidia.com/cuda/cuda-driver-api/group__CUDA__CTX.html . All data remains owned by that context and modules. Context creation, code loading, allocation growth and subsequent reuse are separately recorded.

Ordinary row assertion, target-domain or source-budget failure does not poison other rows or later calls. A Driver failure discards all owned allocations/modules/context before a later retry; cleanup attempts every release and preserves the primary error. Context restoration or cleanup uncertainty marks the session unusable for further runs. Close may retry destruction of retained handles after a failed cleanup. Closed sessions reject execution.

Focused verification: normal and optimized Python each pass 20 offline tests, with one class-level device-unavailable skip covering five actual-device tests. Eight new lifetime tests cover code/context/buffer reuse, growth and shrinking, source snapshot and metadata copies, source drift, entry cache bound, lane errors followed by success, invalid input recovery, injected launch/allocation failures, all-release cleanup, primary-error preservation, failed destruction retry, failed context pop, thread migration and lock serialization. The actual-device additions exercise reuse across entries and growing batches, assertions/domain errors, caller-context restoration and closing from another host thread. Parent-owned actual-device results are retained separately.

Independent review by the CPU owner also exercises an eleven-fault Driver matrix; its source-bound report is separate from this implementation note. No device execution or speedup is inferred from fake Driver tests.

The exact original pre-session implementation and tests are retained as `gpu_compiler-before-session.py` and `test_gpu_compiler-before-session.py`, with `BASELINE_BINDINGS.json`. The current one-shot API includes the new source snapshot and explicit context restoration. A benchmark against current one-shot should be labeled session-per-call versus reusable session; a historical-baseline claim requires executing the retained older bytes. Inclusive comparisons must include construction, all calls, close, and materialization/serialization chosen by the application. Per-call timings intentionally exclude final session close, which is reported separately in session stats. No speedup is claimed in this implementation record.
